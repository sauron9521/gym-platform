# Fresh PostgreSQL baseline — 14 November 2026

The initial Prisma migration at `apps/api/prisma/migrations/20261114000000_initial_baseline/migration.sql` was regenerated directly from the **current Prisma Schema**, before the first Gym Platform production database. Only one migration directory is active.

## How the migration was generated

From `apps/api/`, with Prisma ORM v7 and the repository's lockfile:

```sh
pnpm exec prisma migrate diff --from-empty --to-schema prisma/schemas --config prisma7.config.ts --script -o prisma/migrations/20261114000000_initial_baseline/migration.sql
```

The generated SQL is kept verbatim at the beginning of the file. We appended one PostgreSQL `CHECK` constraint, `body_measurements_at_least_one_metric`, because Prisma Schema does not currently model that constraint. The three partial unique indexes, foreign keys, other indexes and types are **generated by Prisma** from the current schema (including `partialIndexes`).

Unlike the earlier historical SQL squash, this baseline contains no intermediate schema changes or redundant drop/recreate operations. The 24 former migration hashes remain archived **only as audit metadata** in `apps/api/migration-baseline.json`; they must not be applied.

To verify that the committed generated section still matches the current Prisma Schema, run:

```sh
pnpm --filter @gym/api db:baseline:check
node --test apps/api/test/migration-baseline.test.mjs
```

## Required empty-database setup

This is **not an upgrade** from the old migrations or the previous SQL-squash baseline. If a local or staging database has either history recorded in `_prisma_migrations`, discard/recreate only that explicitly identified disposable database before proceeding; migration checksums are now different. Never run these commands against a production database with data.

```sh
pnpm --filter @gym/api db:generate
pnpm --filter @gym/api db:validate
pnpm --filter @gym/api db:baseline:check
pnpm --filter @gym/api db:migrate:deploy
pnpm --filter @gym/api db:migrate:status
pnpm --filter @gym/api db:seed
```

CI must verify a clean PostgreSQL 17 migration, seed, integration/e2e behavior and manually preserved constraints before merging.

## Release compatibility

Images released before the baseline reset cannot perform a forward migration on an existing schema initialized by the new baseline. Any two-release staging upgrade/rollback proof must use releases prepared **after** this reset.

Once any persistent database exists, treat migration history as immutable and add a new forward-only migration for each schema change. Do not rewrite this baseline after production or any non-disposable environment adopts it.
