## Acceptance evidence

- **Canonical contract:** full OpenAPI JSON deep equality across both pinned commits, 85 paths and 107 unique operation IDs. Generated TypeScript AST equality after sorting interface members and declarations. All seven relationship operations and two dashboard operations retain their HTTP contracts.
- **Controller parity:** both original controller class ASTs are identical after printing without comments, including decorators, method names, bodies and parameter types. Existing operation identities and stock throttling keys remain stable. Dashboard response constants moved unchanged in #957, and the canonical schemas match.
- **Dependency boundaries:** the two TrainerAthletes application services, Exercises controller, Workouts service and TrainingPrograms assignment service differ from baseline only by their explicit public-contract imports. Existing Exercises context is a type-only re-export, not a new runtime module dependency. Core retains the sole UsersModule feature dependency. Real Nest probes verify singleton service/repository/transactional provider ownership, two separate controller owners and no core controllers.
- **Persistence and authorization:** the checked Prisma paths, API manifest, lockfile, frozen inventory, validator, Auth/Users modules, common auth and rate policy, TrainerAthletes repositories, DTOs, types, selectors, domain/policies and private termination/copy services are unchanged. Existing transaction-level capability rechecks, recipient-only accept/decline, initiator cancellation, revoked-trainer cleanup, bounded dashboard projections and owner isolation are preserved. No new role gate.
- **Historical relocation:** the map equals the baseline plus precisely two original relationship controller/spec entries. The dashboard controller/spec were absent from the frozen inventory; no artificial entries. Original registry remains in place and pins an empty core.
- **Architecture:** five real audience roots (Public, Shared, Athlete, Trainer, Admin), with 59/107 canonical operations audience-owned. The remaining 48 include unmigrated features and operational routes. The total is not a release-readiness metric.

## Business core organization

During ABI01–ABI08, retain the existing feature-first `modules/` layout and explicit public contracts. Controller-free feature modules serve as the current business core in a conceptual sense; this does not imply framework or persistence independence. The owner explicitly deferred the final structural decision until after completion of all architecture migration stages. At that point, review the benefits, dependencies and composition trade-offs of retaining the current layout, introducing an aggregate CoreModule or a core directory, or extracting a separate package. None of those alternatives is approved or rejected by this review. API leaves continue importing only their required feature modules; infrastructure and common technical mechanisms retain their existing ownership. Future worker composition and separate deployables still require evidence and separate approval.

## ABI06d — proposed Exercises sequence

The current ExercisesModule has ten operations in two controllers. Four existing GET routes under ExercisesController are optional-authenticated and include both public catalog and authenticated visibility behavior. Three mutations use the existing actor/capability/scope policies across users, trainers and admin. Three trainer-access routes are athlete-owned grants. Preserve these semantics; audience is an organizational boundary, not a new role restriction. In particular, do not treat optional-authenticated reads as anonymous-only or as a separate public-only catalog, and do not introduce duplicate admin/athlete/trainer mutations.
