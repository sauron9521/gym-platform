## Decide whether an operation needs a boundary

Use the checklist on one complex write in its owning feature issue. Favor operations with an explicit state transition, competing writes, eligibility to recheck at commit time, or an external provider boundary. Keep ordinary CRUD and read projections in the existing module structure. The extra boundary should isolate a rule, protect an atomic operation, or make a material failure easier to test.

1. **Pin the behavior.** Identify the actor, resource or tenant, permitted state transitions, HTTP contract, external side effects and transaction ownership. Record the baseline commit and the regression that would catch a behavior change.
2. **Separate the policy and the write where useful.** Put pure rules and transition tables in the owning domain. Define an application command and specific outcomes for expected failures. Add a narrow port when a provider or transactional operation benefits from substitution. Keep Nest composition, Prisma projections and provider I/O at their existing outer boundaries.
3. **Prove atomicity and scope.** Recheck authoritative state and eligibility under the transaction or conditional write that owns the change. Preserve lock order and rollback. For replayable input, identify the source of the idempotency key and verify that repeated, out-of-order or competing inputs cannot repeat the business effect. For external delivery, follow the feature's persisted-event and retry policy.
4. **Verify and record.** Cover pure rules with deterministic tests, ownership and ordering with real PostgreSQL tests, and authorization and contract parity at the HTTP boundary. Run `architecture:deps` and its fixtures for any new opt-in, including type-only imports. Link the targeted tests and successful final CI to the owning issue. Review the added surface against the observed benefit before broadening the refactor.
